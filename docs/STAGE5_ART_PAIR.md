## Animation implementation and actual limits

Each 960×640 WebP atlas has four 480×320 tiles: rest, anticipation, impact, recovery. CSS background positions select the tiles; this moves the actual arm/tool poses, **not a transform/zoom of the entire card**. A 900ms timeline displays frames0→1→2→3→0 and then clears the sprite. Four key poses are a short flipbook sample, not a smooth rigged animation; some generated background/pose continuity remains approximate. Final smooth motion would need consistent 8–12 rendered frames or a commissioned rig, not marketing claims that four images are a complete animation production.

Only one action can run or load as active at a time; a new action cancels previous timers. Touch/pointerdown starts without delaying click/navigation; hover only on hover-capable devices, keyboard focus also triggers. Replay buttons demonstrate the action without leaving the cards. No autoplay/loop/video/audio/3D runtime, no persistent requestAnimationFrame. Still posters form the complete card. Atlases are fetched only on interaction and reused from image cache; errors preserve poster and show localized status. Reduced motion, Save-Data, unchecked motion and hidden page stop/suppress actions. Reload resets the optional review toggle; it does not alter game data preferences.

Code: `web/art-pair/cards.js`, `style.css`, `config.js`; assets/contract/hashes: `assets/art-pair/manifest.json`. Runtime art has no remote URL or external font. Masters are backed up privately, not in the public repo. Compression is deterministic atlas extraction/downsampling/encoding, not a replacement illustration or painted edit. Manifest and runtime timeline are tested.
