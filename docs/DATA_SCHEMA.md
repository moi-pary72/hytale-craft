# Форматы данных Hytale Craft

## Четыре независимые категории

1. `data/recipes/hysphere-YYYY-MM-DD.json`, schema 3: реальные игровые записи из публичного экспорта независимого источника, проверенные на структурную полноту. `status: source-backed` **не означает официальную проверку** и не подтверждает текущую game build.
2. `data/catalog.json`, schema 1: только ID OpenHytale. `recipe_ids` никогда не используются как рецепты. Старый набор не дополняет и не исправляет более новый.
3. Пользовательские рецепты в `localStorage['hytale-craft-recipes-v1']`: старый формат `{name:{yield,source,ingredients}}`. Они не меняют source-backed snapshot.
4. Синтетические объекты в тестах: явно fixture/test, не входят в опубликованную базу.

## Snapshot schema 3

`source`: name, url, license_url, usage, extracted_at, revision, game_version, exact_build, verification, raw_sha256. У HySphere `game_version='Early Access'`, `exact_build=null`. Дата извлечения известна, точная версия неизвестна. Поля не дополняются предположением.

`items`: уникальные `{id,names:{en,ru},category}`. Английское имя — из источника, русский null при отсутствии перевода. Категории нормализованы для UI. Фраза «Простой короткий лук» используется как введённый пользователем поисковый псевдоним `Weapon_Shortbow_Crude`; интерфейс не выдаёт её за официальный перевод.

`recipes`: уникальный id, inputs/outputs массивы `{kind:'ItemId',id,quantity}`, bench_requirements, time_seconds, knowledge_required, status, source_url. Разрешены только известные ItemId и положительные целые количества, один выход. Одинаковые outputs разных recipes не схлопываются: нужен выбор альтернативы. Дублирующиеся ингредиенты суммируются калькулятором с ограничением переполнения.

`bench_requirements`: список из исходного экспорта; id/type/categories/tier сохраняются. `tier=null` — неизвестно, не нулевой уровень. UI показывает перечисленные источником станции; не вычисляет из количества entries, нужно ли строить все станции. Requirements сохраняются для каждой операции, не добавляются автоматически в список ингредиентов. Время и knowledge не выдумываются.

`incomplete_recipes`: `{id,outputs,reasons}`. Включает записи с missing material, неизвестной станцией, несколькими выходами и salvage. В source-backed recipes они не входят. В отчёте причины пересекаются, поэтому их количества нельзя складывать как число записей.

## Политика расчёта

Цели и инвентарь — original ID → количество. Все цели одного плана используют один snapshot и общий stock. Выход округляется до партий; излишки доступны после изготовления ингредиентов. Инвентарь учитывается, но не списывается в хранилище. Материалы без поддерживаемого рецепта остаются в списке «Нужно получить», это не утверждение об их добыче в природе. Известный неполный рецепт отмечается предупреждением.

Граф может включать настоящие обратимые преобразования. При цикле расчёт останавливается. Пользователь может явно отметить промежуточный предмет «получить отдельно»; граф обрывается на нём и он попадает в список приобретения. Это не изменение исходного рецепта и не автоматическое угадывание альтернативы. При нескольких рецептах требуется выбор; есть UI для root и промежуточных вариантов.

План source-backed рецептов сохраняется по `hytale-craft-plan-<source revision>`, старые планы другой версии не смешиваются. Инвентарь использует существующий browser key; IDs и пользовательские названия не сопоставляются догадкой.

## Контрольные суммы и обновление

`data/recipes/manifest.json`: active, path, sha256. SHA-256 проверяется браузером **до** загрузки рецептов. JSON пути ограничены именем файла. При неверном хеше рецепты не используются, доступен старый ID-only каталог с сообщением.

`source.raw_sha256` — вычисленные при получении checksum исходных HTTP-ответов. Это подтверждение воспроизводимости полученных байтов, **не подпись автора**. HySphere не публикует upstream checksums в manifest. Передача идёт по HTTPS к фиксированным документированным endpoints. Нет обхода авторизации или парсинга HTML.

При новой дате создаётся отдельный snapshot, старые версии сохраняются. При изменении того же snapshot сохраняются `.previous.json` для него и manifest; пустые/повреждённые/сократившиеся более чем на 20% кандидаты отклоняются. Все изменения через PR и ручной merge. Actions diagnostics не равны успешному recipe import.

## Assets.zip review candidate

Импортёр пишет schema 3 в `.private/` и `verification: local-review-candidate; not published`, recipe status candidate. Он не может быть загружен UI как source-backed snapshot. Требуется отдельный просмотр и адаптация с происхождением и разрешением публикации.

Поддерживаются standalone и embedded Recipe, исходные ID, inputs/outputs/PrimaryOutput, количество, станция, metadata, time, knowledge/memories. Parent разрешается отдельно в Items/Recipes, массивы заменяются, вложенные объекты переопределяются рекурсивно по документированному default. Циклы, неизвестный родитель, дубль ID, плохой JSON и большие архивы отклоняются. Специфичные движку merge-исключения остаются непроверенными без настоящего архива.

ResourceTypeId и ItemTag сохраняются как группы, без произвольного выбора предмета; несколько outputs и material Metadata сохраняются как неподдерживаемые для расчёта. Неполные ссылки перечисляются явно. Файлы с ошибками не заменяют предыдущий candidate; report описывает отказ. Сложные групповые механики требуют проверки на разрешённой game build.
